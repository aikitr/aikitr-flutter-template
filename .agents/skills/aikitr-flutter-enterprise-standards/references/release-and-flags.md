# 5. 发布、功能开关与兼容窗口

## 发布契约

每个 release record 包含版本/build、commit、SDK/Xcode、环境、产物摘要/符号、后端协议范围、schema 最小读写版本、必要开关、验收证据、owner 与止损方案。发布流水线的构建、签名、分发和生产配置操作分别标记权限。

支持窗口声明最低客户端版本、旧版后端兼容范围、数据降级策略与停止支持方式。客户端升级率不足时不能假设所有消费者已经使用新字段；协议采用可容忍的新增和明确的 breaking version。

先扩展兼容后端/格式 → 发布可兼容新旧协议的客户端 → 观察采用率与关键指标 → 受控开启 → 到达停止支持条件后移除旧路径。数据库 schema 变更遵循 [持久化演进](persistence-and-evolution.md)，不能仅回退二进制来修复不可逆迁移。

## 功能开关模型

开关是类型化、可验证的配置：key、类型、默认值、owner、用途、作用域、配置版本、更新时间、有效期、兼容的应用/协议/schema 版本、移除日期。默认值依据业务风险决定，不一概开启或一概关闭。

| 失效情形 | 必须定义的行为 |
| --- | --- |
| 远程配置不可用/离线 | 使用仍有效且兼容的 last-known-good，或安全本地默认值 |
| 过期/格式错误/未知配置版本 | 拒绝该配置并记录原因；不以未验证值替换可信快照 |
| 切换账号/租户/环境 | 重新验证作用域；不能沿用另一主体 cohort/config |
| 开关改变解析器/数据格式 | 绑定对应 parser/schema/cache namespace，只有兼容组合才生效 |
| 交易进行中配置变化 | 操作持有一致配置快照/操作版本；紧急终止按后端状态协议处理 |
| 旧客户端不认识 key | 使用已定义默认行为，后端仍保持支持窗口内兼容 |

配置更新原子地发布可信快照，验证所有相互依赖字段；不得让一半新值一半旧值被业务读取。回退开关也需验证数据/协议兼容，不能把成功解析的新数据交给旧 parser。

开关管理入口与生产分发有审计、权限和变更记录；发布前验证 offline/fallback。remote flag 不能代替服务端授权或保管秘密，也不默认拥有下载执行代码、绕过平台发布规则的能力。

## 灰度、实验与止损

灰度定义目标平台/版本/环境、稳定 cohort、流量比例、观测窗口、最小样本、成功/异常指标、自动暂停条件和负责人。账号级体验需要稳定分组，不能每次请求随机翻转；采集用户标识按隐私策略处理。

逐级扩大前比较同口径的成功率、失败/崩溃、性能和关键结果；灰度比例及阈值由项目风险与样本决定，不默认固定“1%-10%-100%”适用于所有业务。

实验有假设、主指标、护栏指标、期限和结束决定；开关结束后删除代码分支、配置、测试及遥测字段的过期依赖。安全/支付协议不因实验分组放宽。

止损方案区分：关闭尚未开始的新流程、阻止危险操作、服务端兼容修复、发布新包和必要的升级引导。已发生交易不能靠 flag 反向撤销。移动 App 安装与商店传播有延迟，关键安全条件需后端控制，不能承诺瞬时全量回滚。

## 验收与模板

验证新/旧 App × 新/旧协议 × 在线/离线配置 × 旧/新 schema 中实际支持的组合；覆盖配置到期、签名/来源校验失败（采用时）、账号切换、开关翻转过程中交易、新 parser 缓存与旧 parser 不兼容。

发布 owner 保存 release checklist 与对应证据，模板见 [release-checklist.md](../assets/templates/release-checklist.md)。生产开启/关闭和上传商店按用户授权与团队权限操作；规范技能本身不授权发布。
