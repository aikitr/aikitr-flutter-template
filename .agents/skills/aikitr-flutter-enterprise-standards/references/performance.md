# 3. 性能与资源预算

## 预算与证据

性能要求先定义测量口径、代表设备、系统/屏幕刷新率、网络/数据集、构建模式、样本数量、绝对目标与相对回归容忍度，再决定优化。目标由产品与工程共同确认，不将某个机型的结果作为所有设备的保证。

| 指标 | 必须固定的口径 |
| --- | --- |
| 冷启动/温启动 | 进程冷暖、首帧与首次可交互分别计时；包含必要初始化 |
| 关键路径耗时 | 开始/完成事件，缓存命中与网络路径分组，p50/p95 与失败率 |
| 帧性能 | UI/raster 分别观测，刷新率对应预算，慢帧比例与连续卡顿 |
| 内存 | 稳态、峰值、重复进入退出后的残留；包括图片/原生资源 |
| 包体 | download/install 或目标构建体积，架构/资源与符号条件一致 |
| 网络/存储 | 请求数、传输量、缓存占用、后台流量，按场景和窗口统计 |

使用 profile/release 和代表设备；debug 测试不作为发布性能证据。Flutter 的帧分析与 build/layout/paint 建议见 [性能指南](https://docs.flutter.dev/perf/best-practices)。预算示例模板见 [performance-budget.yaml](../assets/templates/performance-budget.yaml)，填写项目数值后才作为门禁。

## UI 与计算

- build 保持廉价、无 IO/提交；按变化范围拆 Widget，使用 const、局部订阅/select 等适用手段，避免只因文件长而拆分。
- 长列表/grid 使用 lazy builder，稳定 key、分页和有界数据集；确有已知固定尺寸时利用相应能力，不能测不准还强设 itemExtent。
- 谨慎使用 intrinsic layout、saveLayer、opacity/clip 和同时播放的大量动画；定位渲染成本再调整，不为规避性能盲目删除设计效果。
- 图片按显示尺寸及实际 pixel ratio 解码，压缩/占位/失败路径与内存缓存有预算；不能只限制网络文件大小而忽略解码内存。
- 对大量 JSON、排序、压缩等先测量再使用 isolate，计算消息传递/复制和启动成本；isolate 不自动支持 UI 或全部平台插件。
- 按 debounce/cancellation 策略减少过时搜索；服务端分页不以一次下载所有数据替代。

## 生命周期与资源

对象 owner 创建与释放 controller、订阅、计时器、文件/数据库句柄、图片流、原生 view 和后台 worker。长生命周期服务与页面资源分开，provider/cache 保留有明确理由与容量。

不把 BuildContext、Widget、临时 callback 或大原始 payload 作为全局缓存。页面离开后仍需完成的业务任务转交对应业务生命周期，不能仅让页面 controller 永不销毁。

恢复前台不创建重复轮询/订阅。资源紧张时按优先级释放可重建内容，必须保全关键业务记录；平台内存压力通知与关键场景观察可提供依据，不能假定通知总能及时抵达。

## 验收与门禁

定义少量稳定基准：冷启动、长列表滚动、图片密集页、编辑/返回循环及关键提交路径。按相同构建/设备/数据测量并记录版本、样本和分位数，CI 不用一次噪声值判定全部回归。

可重复的性能基准可进入专用 runner；共享 CI 设备噪声高时，采用复测与人工审查规则，同时保留绝对风险上限。批准回归记录理由、影响、owner 与到期计划，不改历史基线来掩盖回归。

每个发布至少确认关键路径预算、无持续内存增长和包体变化原因；新图片/字体/原生 SDK 提交附体积或资源影响。团队提供可重现输入和 DevTools 证据，不仅写“已优化”。
